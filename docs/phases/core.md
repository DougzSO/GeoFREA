## Active implementation decisions

- **D-core-001 — Technology-level discount rate.** IRENA reports genuinely different discount rates per technology for the same country, so `discount_rate` lives under `parameters.json`'s per-technology entries, never at country level.
  Archive: docs/_archive/2026-09/DECISIONS.md 2026-08-20 - discount_rate architecture fix
- **D-core-002 — Solar and wind parameters from IRENA.** Solar and wind cost/performance parameters (CAPEX, OPEX, lifetime, capacity factor) are populated from IRENA 2024/2025 editions, differentiated per country where the source provides country-level figures.
  Archive: docs/_archive/2026-09/DECISIONS.md 2026-08-20 - solar and wind parameters populated (IRENA 2024/2025)
- **D-core-003 — Single orchestration and audit mechanism, implementing A-01/A-02/A-03/A-09 (verdicts OQ-E2-1 to OQ-E2-4; E4 artifact-granularity closeout).** `PhaseSpec` carries `requires`/`produces`; `Orchestrator.run()` validates the graph (`MissingProducerError`, `DependencyCycleError`, `DuplicateProducerError`) and topologically orders phases (stable tie-break by name) from `RunConfig.target_phases`/`rerun_phases` (see D-core-012 for `rerun_phases`, which replaced `force_rerun` in R-1). `PhaseContext.register_artifact()` feeds `RunManifest.artifacts` (path, sha256, size, mtime, schema_version, phase, run_id), reused when size/mtime match and integrity-checked (missing file or hash mismatch, never recomputed) whenever a phase is resumed *or* loaded as an upstream artifact outside the current run's target set. `RunManifest.schema_version` is pinned `"2.0"` (`LegacyManifestError` otherwise, no migration). A failure records `status="failed"` without raising; dependents get `"skipped_upstream_failed"`; independent branches still run. Artifact granularity per phase: F1 (`data_acquisition`) and F1b (`data_quality_audit`) register one artifact each — a JSON dump of the whole phase output (`layer_registry`, `audit_report`) — because neither phase's output has natural per-item files to hash separately (F1b's report is one document; F1's `AcquiredLayer` entries have no per-layer checksum today, see OQ-024). F2a (`grid_alignment`) registers one artifact per aligned raster field (`aligned/<layer>`, `main.py::_register_aligned_rasters()`) plus the `aligned_rasters` JSON summary, since each raster is independently a real, hashable, resumable file. F2b (`suitability_criteria`) still registers only its own output model as one artifact (see Known issues) — unlike F1/F1b, this is a temporary exception, not the final design, pending the Estágio H rebuild.

Carried forward into M-F2b-01 E4 (`slope_max_deg[tech]`), same underlying rationale.

- **D-core-012 — `force_rerun`'s cascade replaced by explicit `rerun_phases` scope plus manifest-recorded staleness (R-1, 2026-09-23).** Verdict on the draft below (History): `RunConfig.rerun_phases: list[str]` (`schemas.py`) replaces `force_rerun: bool`. `Orchestrator.run()` (`orchestrator.py`) re-executes exactly the phases named in `rerun_phases` — no consumers-graph walk seeds execution scope anymore; `to_attempt` is only `needed` (`target_phases`'s transitive closure over `requires`). A name in `rerun_phases` outside `needed` is a `MissingProducerError`, following the pre-existing `unknown_targets` pattern (same exception type, same validation style, checked immediately after it). After a named phase completes successfully, every phase in its transitive `consumers` closure that currently holds a `"success"` manifest entry is rewritten to `PhaseManifestEntry(status="stale_upstream", invalidated_by=<the rerun phase>, invalidated_in_run=<this run's run_id>)` — this rewrite happens in the same in-memory mutation pass as the rerun phase's own success entry, both persisted by the single `self._write_manifest()` call that follows (`orchestrator.py`, end of the success branch in `run()`): nothing is written to disk until every mutation for that phase's completion — its own entry and every downstream staleness marking — is already applied in memory, so a crash either persists all of it or none of it; there is no intermediate on-disk state where the rerun phase is `"success"` but a dependent it invalidated is still recorded `"success"`. `stale_upstream` is not `"success"`, so the existing resume check (`if not must_force and existing is not None and existing.status == "success"`) already never resumes it — no separate check was needed. A phase holding `stale_upstream` that the current run's `needed` closure requires is therefore recomputed automatically the next time any run needs it, whether or not `rerun_phases` names it that run. **Accepted cost:** invalidation is triggered by the upstream phase having *re-executed*, not by its output having actually *changed* — a rerun that reproduces byte-identical output still marks every downstream consumer `stale_upstream` and forces a real recompute next time, with no cheaper "output was actually identical, skip the recompute" path. See OQ-031 for whether a future revision should compare artifact hashes before marking dependents stale, cross-referencing OQ-026 (the alignment/audit caches this same manifest signal partly answers already). Manifest `schema_version` bumped `"2.1"` → `"2.2"` (`PhaseStatus` gained `"stale_upstream"`; `PhaseManifestEntry` gained `invalidated_by`/`invalidated_in_run`, both optional, defaulting to `None`) — a `"2.1"` manifest on disk is read and its version tag normalized to `"2.2"` in memory before validation (`Orchestrator._load_manifest()`), not migrated by a separate script, since the new fields' `None` defaults make old JSON already valid against the new schema; only pre-`"2.1"` manifests still raise `LegacyManifestError`. `settings.yaml`'s `run.force_rerun` key renamed to `run.rerun_phases` (default `[]`); `config_loader.load_settings()` fails loud with a message naming `rerun_phases` if a settings file still carries `force_rerun`, rather than relying on `RunConfig`'s `extra="forbid"` alone (which would reject it but not say what replaced it).
  Draft superseded below in History.
