## Active implementation decisions

- **D-F1b-004 — slope removed from config/audit.yaml; F1b never audits it (resolves OQ-030).** Applied the "remove" option, not the "give it a distinct report status" option: slope is not produced until `grid_alignment` derives it from the DEM (`raster_alignment.derive_slope_from_dem()`), so F1b has no file to hold an expectation about in the first place — a permanently-null config entry misstated this as an open sourcing question when the real fact is a phase-ownership one. `AuditInputs.slope_path` stays in the schema (still reports `[MISSING] SLOPE: File not found` today, a status distinct from `not_audited` since the resolution check never runs for a layer whose inspection already errored) — only the `config/audit.yaml` entry and its OQ-030 backing are gone. See docs/phases/F2a_grid_alignment.md Known issues for where the expectation now belongs. Caveat: if `slope_path` were ever populated (AuditInputs' own docstring calls this "usually None", not "never"), `diagnose_consistency()` would silently skip its resolution check — same class of silent gap already tracked for `population` above, not a new one introduced here.
- **D-F1b-003 — land_cover tile cache: sha256 content check added; hit condition and its remaining gap recorded, OQ-026 extended.** Cache mechanics as of `raster_inspection.py` (`_land_cover_tile_cache_key`, `_load_land_cover_tile_cache`/`_save_land_cover_tile_cache`, called from `inspect_land_cover_tiles()`; wired in `audit.py`'s `land_cover_cache_dir`): one JSON file per tile at `outputs/<country>/data_quality_audit/land_cover_tile_cache/<tile_stem>.json`, holding that tile's CRS, resolution and per-class area contribution. A hit requires the tile's mtime, size, and sha256 of its own bytes, plus a sha256 of the masking country polygon's WKB, to all match a `cache_key` string stored alongside the payload — not path existence alone. Added 2026-09-23: the sha256 of the tile's bytes (`_file_sha256()`), closing the gap where the first version (2026-09-22, mtime+size only) could not tell a same-size/same-mtime content change (e.g. a tile silently re-downloaded or restored with a copied timestamp) from an unchanged tile. The polygon fingerprint already covered a changed island-filtering rule or a different `country_gdf`. Remaining, real gap: the key carries no version of the per-tile computation algorithm itself — if `inspect_land_cover_tiles()`'s class-area logic changes (a bug fix, a different windowing strategy), an old cache entry computed under the prior logic is silently reused forever, since nothing about the code version is in the key. Added as a second instance to OQ-026 (`docs/OPEN_QUESTIONS.md`), alongside the grid_alignment mosaic/interim caches — no key design proposed here, per that OQ's resolution protocol. A change to `excluded_land_cover_tiles` does NOT create wrong results for tiles that get processed (it only changes which tiles are even in the list passed in; a tile's own cached result doesn't depend on which other tiles were excluded) — this is not a vulnerability of this cache, unlike the algorithm-version gap above.
- **D-F1b-002 — M-F1b-01 expectations moved to config/audit.yaml, sourced from native file metadata.** `audit.py`'s five hardcoded literals (`_EXPECTED_RESOLUTIONS_DEG`, `_RESOLUTION_TOLERANCE`, `_SOLAR_PVOUT_SANITY_RANGE`) are gone; `run_audit_phase()` now takes an `AuditConfig` (loaded from `config/audit.yaml`) and `diagnose_consistency()` returns `(alerts, not_audited)`. Every configured value's `source` is either a primary reference or the layer is `null` with an OQ ID (OQ-027 to OQ-030) — resolved by reading GDAL metadata directly off the BRA/PRT files on disk (land_cover 0.0000833 deg, solar 0.0083333 deg, elevation 0.005 deg, wind-speed 0.0025 deg — all agreeing across both countries). PVOUT's unit was corrected to `kWh/kWp/day` (file's own XML metadata; matches M-F1-02 — the divergence was in the code, not METHODOLOGY). `slope` has no entry at all (see D-F1b-004: it's a grid_alignment-derived product, never an F1b input — removed, not left null). Layers with no fetch path at all (3 GWA products, CMIP6, ERA5, GEM) are now reported `not_audited` unconditionally instead of omitted. `AuditResult` gained `not_audited: dict[str, str]`; `AuditSummary` gained `n_not_audited`.
- **D-F1b-001 — Vector inspection distinguishes read_error from processing_error; WDPA repair is no longer audit-specific.** `inspect_vector_layer()` used to swallow both a file-open/clip failure and a downstream statistics failure into one `error` field, labeled "found (unreadable)" — indistinguishable without reading logs. Two try/except stages now set `error_type` (`"read_error"` | `"processing_error"`), and `VectorLayerSummary.status` mirrors that split in the audit report footer. Separately, the `[ERROR] found (unreadable)` PRT/protected case (`TopologyException: side location conflict`, confirmed pre-existing against unmodified commit `e1a57ed`, see History) was resolved as a side effect of moving invalid-geometry repair into the shared `clip_vector_to_country()` — not touched here directly. Real PRT run 2026-09-21: 14/184 WDPA features repaired (`Too few points in geometry component` x7, `Self-intersection` x5, `Ring Self-intersection` x2), `protected` now reports `[OK] found`.

## Known issues

- `audit_report`'s artifact `schema_version` was bumped to `"2.1"` 2026-09-22 (main.py `_AUDIT_REPORT_SCHEMA_VERSION`) when `AuditResult` gained the required `not_audited` field (D-F1b-002) — a manifest entry recorded under `"2.0"` or earlier now correctly raises `StaleManifestEntryError` on resume instead of a raw Pydantic `ValidationError`.
- `population` has no configured `expected_resolution_deg` in `config/audit.yaml` and is not in the `not_audited` set either — it was never checked before D-F1b-002 (no literal existed for it in the old `_EXPECTED_RESOLUTIONS_DEG`) and F7-1/F7-2 did not extend scope to it. M-F1b-01 technically requires it; tracked here as a gap, not an OQ, since no research is needed — it just needs a metadata read like the other four.
- Land-cover inspection for BRA takes about 37-55 minutes. Per-tile caching implemented 2026-09-22, hardened 2026-09-23 — see D-F1b-003 for the cache's exact mechanics and its remaining gap (OQ-026). A run interrupted partway (real incident, 2026-09-22: a computer suspend killed a BRA run near tile 60/112) now resumes from the last cached tile instead of restarting from zero.
- `audit_report`'s artifact `schema_version` was bumped to `"2.0"` 2026-09-21 (main.py `_AUDIT_REPORT_SCHEMA_VERSION`) when `VectorLayerSummary.status`'s literal set changed — a manifest entry recorded under `"1.0"` now correctly raises `StaleManifestEntryError` on resume (METHODOLOGY A-02/A-09, docs/phases/core.md) instead of a raw Pydantic `ValidationError`. Any future breaking change to `AuditResult`'s shape needs the same bump.
- The 2026-09-22 FD4c `force_rerun` audited the corrected, geometry-filtered `land_cover` registry (BRA 112/155 tiles, PRT 11/26 tiles — see `docs/phases/F1_data_acquisition.md` Known issues) end to end; both audits completed and reported `success`. BRA's land-cover inspection took ~55 minutes this run (up from the ~37-minute figure above, consistent with more real per-tile geometry work now happening, not a regression).
