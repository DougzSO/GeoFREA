### Finding (not changed): staleness follows the file hash, not the content

A phase is marked `stale_upstream` when the SHA-256 of an artifact changes. The parquet writer puts provenance in the file metadata, so a re-run that writes the same table changes the hash and invalidates the consumers. Here it made F5 and `potential_maps` stale in the three countries although `forcing.parquet` is content-identical. The effect is a rerun that was not needed (F5 BRA is 10 minutes); no result is wrong. Making the manifest compare a content digest instead of the byte hash is a change of A-02 and it was not asked, so it is not done.

## 3. OQ-060 (step 3, branch `fix/oq060`)

### 3a. Diagnosis (read only, F3 tables of 2026-10-17)

The elevation of a cell is the eligible-area-weighted mean of the aligned DEM, so it is NaN where no eligible pixel has a DEM value (also in every cell with no eligible area). Cells with at least the minimum eligible area and NaN elevation (the ones that matter), by scenario (restrictive / central / permissive):

| Country | Technology | Cells (km2 of eligible area), central | Restrictive / permissive | Were they candidates before? |
|---|---|---|---|---|
| PRT | solar, wind | 0 | 0 / 0 | n/a |
| IND | solar | 14 (4.51) | 12 / 16 | **yes** (solar has no altitude limit) |
| IND | wind | 36 (35.68) | 26 / 38 | no (`elevation <= limit` is false for NaN) |
| BRA | solar | 1 (0.115) | 0 / 1 | **yes** |
| BRA | wind | 1 (0.128) | 0 / 1 | no |

How each criterion treated them: slope (E4) works on the `slope_counts` of the pixel, and a pixel without slope is invalid (`valid_pixels`), so these cells have valid slope, land cover and population but no DEM value in the eligible pixels of the aligned elevation raster (why the two rasters disagree there was not investigated); E1 to E3, E5 and E6 are shares of the pixel and do not use the elevation; the only criterion that touched the cell elevation was the altitude limit of wind, which dropped the NaN cells without counting them (`n_cells_excluded_by_elevation` counts `> limit`). So **solar did not exclude them, by no criterion**; wind excluded them by accident. The stability table used `elevation > limit`, so it kept the NaN cells of wind that the candidate tables had dropped (an inconsistency).

### 3b. The rule

`config/experiments.yaml`, `land_availability.missing_elevation: ineligible` (the only value the model accepts). A cell without elevation is not a candidate, for both technologies and every land scenario; the limit of 3000 m is evaluated only on cells that have an elevation. `candidate_exclusion_reasons` (`land_eligibility/scenarios.py`) returns `missing_elevation` or `elevation_max` for a cell with enough eligible area, and the candidate filter, the stability table and the counts use it. `TechSummary.candidate_exclusions` holds the counts of the central scenario. The eligible area of the cell tables is not changed: the rule acts on the candidate set (the tables of cells keep the cells with their area). Tests: `tests/unit/test_land_eligibility_pipeline.py`, four new (a NaN cell has `missing_elevation` for both technologies; a cell at 3100 m is a candidate for solar and `elevation_max` for wind; the same rule in the filter and the stability table; the key in the configuration and no other value).
