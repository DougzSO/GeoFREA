## Active implementation decisions

- **D-F4-001 — Resource and hazard channels use different products by design, never combined.** The resource channel (`delta_rsds`, `delta_wind`, `dT`, M-F4-03) is sourced from raw CDS CMIP6; the hazard channel (`tasmax`/`pr` context indicators, M-F4-05) is sourced from bias-adjusted ISIMIP3b (reused from CRAEI per A-11). Reasoning: a ratio or difference of the same product's own reference and window means cancels a uniform bias to first order, so the resource channel does not need bias-adjustment; an absolute threshold indicator does, to be physically meaningful. The two channels are never arithmetically combined (only read side by side in T-R10), so the product mismatch is not an inconsistency to resolve. Resolves OQ-034(a).
- **D-F4-002 — 2071-2100 hazard data is ISIMIP3b, same product as the core window.** The sensitivity window's `tasmax`/`pr` are acquired from ISIMIP3b, not a different product, because M-F7-07's H1 compares the 2041-2070 and 2071-2100 windows inside one statistical test — a within-test product change would confound that comparison. The ~183 GB / ~2-day acquisition cost (`docs/_audit/2026-09_craei_climate_reuse.md` §5) is accepted. Resolves OQ-034(b).
- **D-F4-003 — A member may carry a resource row with no hazard row.** MIROC6 stays in the resource ensemble per S-04 (satisfiable from the CDS) and has no hazard-channel counterpart, because ISIMIP3b's primary 5-model set does not publish MIROC6 at all — a property of the hazard product, not an acquisition gap. Resolves OQ-035.
- **D-F4-004 — Member contract: channel presence is declared, never inferred from a missing row.** `members.yaml`'s resolved member list carries a per-member field stating which channels that member carries (resource only, or resource and hazard). A member's absence from `hazard_context.parquet` is only ever the expression of a `members.yaml` declaration that member has no hazard channel — never a state a consumer discovers by the row simply not being there. A consumer reading a member from `members.yaml` must check that field before querying `hazard_context.parquet` for it; if the field says the member carries a hazard channel and no row is found, that is a failure (A-09: fail loud, no silent fallback), not an absence to tolerate. Silently treating a missing hazard row as "no hazard data for this member" without having checked the declared field first is not allowed. This is a contract on `members.yaml`'s shape; no schema field name or code is fixed here, that is task J-1's work.
- **D-F4-005 — Member contract needs no METHODOLOGY change.** M-F4-01 defines `m = (gcm, ssp, window)` with no channel notion — D-F4-004 does not add a fourth axis to the member tuple, it only adds a per-member declaration of which of the two already-existing outputs (M-F4-06: `forcing.parquet`, `hazard_context.parquet`) that member appears in. M-F4-06 already gives `members.yaml` a "provenance" field per member with no fixed schema; a channel-availability declaration is provenance-shaped metadata, not a new output or a new member identity. Both items already allow this; no wording change to M-F4-01 or M-F4-06 is needed.
- **D-F4-006 — GCM ensemble selection is not a prerequisite of acquisition (OQ-009).** S-04 requires GFDL-ESM4 and MIROC6 in the ensemble regardless of what M-F4-02's selection protocol later picks for the remaining slots. F-3 acquires those two models first; M-F4-02 chooses the rest in task J-1 against real acquired data, not before F-3 starts.
- **D-F4-007 — M-F4-03's resource-channel input data acquired for the S-04 minimum (task F-3, COMMAND F3-2, 2026-09-27).** Monthly `rsds`/`tas`/`sfcWind` are now on disk for GFDL-ESM4 and MIROC6, `historical` + 3 SSPs, both windows, cropped to BRA/PRT/IND by real GADM polygon intersection, each combination's realization verified (`r1i1p1f1`, identical across every variable/experiment per model) and native grid recorded (GFDL-ESM4 180x288, 1.0x1.25 deg; MIROC6 128x256, ~1.400x1.406 deg) — see `docs/phases/F1_data_acquisition.md` D-F1-015 for the full acquisition record and `cmip6_registry.json` for the registry itself. M-F4-03's `delta_rsds`/`delta_wind`/`dT` formulas are not yet computed — that is F4's own implementation (task J-1), still `not_started` — this decision records that the two-model minimum's resource-channel *input* exists, not that M-F4-03 has run. The remaining ensemble slots (M-F4-02, OQ-009) still need to be chosen and acquired before J-1 can compute change factors for the full approved model set.
- **D-F4-008 — M-F1-05's reduction and reference period settled, no OQ opened (task F4-2, 2026-09-28).** Reduction: annual maximum of ERA5 `fg10` (10 m wind gust since previous post-processing), not `i10fg` and not a percentile — C2 (cut-out, tracker stow) concerns peak events, not a central tendency. Reference period: 1995-2014, coherent with S-05's reference climatology, since M-F1-05 declares the indicator scenario-invariant. Coverage check: ERA5 is production-quality from 1979, so 1995-2014 is fully covered at production quality; no shortening needed, nothing to stop for. Also settled: the daily-maximum reduction commutes with the annual-maximum reduction (`docs/phases/F1_data_acquisition.md` D-F1-016, verified by arithmetic on real probe data), so the CDS derived daily-statistics product is used for acquisition rather than the raw hourly field. M-F1-05 no longer attributes to CRAEI (`docs/METHODOLOGY.md` v1.3.0) — CRAEI's own D12 decided against ERA5 gust, so there was nothing to adapt; the acquisition (task J-2 or a dedicated ERA5 task, TBD in staging) is built fresh.
