## Active implementation decisions

- **D-F4-001 — Resource and hazard channels use different products by design, never combined.** The resource channel (`delta_rsds`, `delta_wind`, `dT`, M-F4-03) is sourced from raw CDS CMIP6; the hazard channel (`tasmax`/`pr` context indicators, M-F4-05) is sourced from bias-adjusted ISIMIP3b (reused from CRAEI per A-11). Reasoning: a ratio or difference of the same product's own reference and window means cancels a uniform bias to first order, so the resource channel does not need bias-adjustment; an absolute threshold indicator does, to be physically meaningful. The two channels are never arithmetically combined (only read side by side in T-R10), so the product mismatch is not an inconsistency to resolve. Resolves OQ-034(a).
- **D-F4-002 — 2071-2100 hazard data is ISIMIP3b, same product as the core window.** The sensitivity window's `tasmax`/`pr` are acquired from ISIMIP3b, not a different product, because M-F7-07's H1 compares the 2041-2070 and 2071-2100 windows inside one statistical test — a within-test product change would confound that comparison. The ~183 GB / ~2-day acquisition cost (`docs/_audit/2026-09_craei_climate_reuse.md` §5) is accepted. Resolves OQ-034(b).
- **D-F4-003 — A member may carry a resource row with no hazard row.** MIROC6 stays in the resource ensemble per S-04 (satisfiable from the CDS) and has no hazard-channel counterpart, because ISIMIP3b's primary 5-model set does not publish MIROC6 at all — a property of the hazard product, not an acquisition gap. Resolves OQ-035.
- **D-F4-004 — Member contract: channel presence is declared, never inferred from a missing row.** `members.yaml`'s resolved member list carries a per-member field stating which channels that member carries (resource only, or resource and hazard). A member's absence from `hazard_context.parquet` is only ever the expression of a `members.yaml` declaration that member has no hazard channel — never a state a consumer discovers by the row simply not being there. A consumer reading a member from `members.yaml` must check that field before querying `hazard_context.parquet` for it; if the field says the member carries a hazard channel and no row is found, that is a failure (A-09: fail loud, no silent fallback), not an absence to tolerate. Silently treating a missing hazard row as "no hazard data for this member" without having checked the declared field first is not allowed. This is a contract on `members.yaml`'s shape; no schema field name or code is fixed here, that is task J-1's work.
- **D-F4-005 — Member contract needs no METHODOLOGY change.** M-F4-01 defines `m = (gcm, ssp, window)` with no channel notion — D-F4-004 does not add a fourth axis to the member tuple, it only adds a per-member declaration of which of the two already-existing outputs (M-F4-06: `forcing.parquet`, `hazard_context.parquet`) that member appears in. M-F4-06 already gives `members.yaml` a "provenance" field per member with no fixed schema; a channel-availability declaration is provenance-shaped metadata, not a new output or a new member identity. Both items already allow this; no wording change to M-F4-01 or M-F4-06 is needed.
- **D-F4-006 — GCM ensemble selection is not a prerequisite of acquisition (OQ-009).** S-04 requires GFDL-ESM4 and MIROC6 in the ensemble regardless of what M-F4-02's selection protocol later picks for the remaining slots. F-3 acquires those two models first; M-F4-02 chooses the rest in task J-1 against real acquired data, not before F-3 starts.
- **D-F4-007 — M-F4-03's resource-channel input data acquired for the S-04 minimum (task F-3, COMMAND F3-2, 2026-09-27).** Monthly `rsds`/`tas`/`sfcWind` are now on disk for GFDL-ESM4 and MIROC6, `historical` + 3 SSPs, both windows, cropped to BRA/PRT/IND by real GADM polygon intersection, each combination's realization verified (`r1i1p1f1`, identical across every variable/experiment per model) and native grid recorded (GFDL-ESM4 180x288, 1.0x1.25 deg; MIROC6 128x256, ~1.400x1.406 deg) — see `docs/phases/F1_data_acquisition.md` D-F1-015 for the full acquisition record and `cmip6_registry.json` for the registry itself. M-F4-03's `delta_rsds`/`delta_wind`/`dT` formulas are not yet computed — that is F4's own implementation (task J-1), still `not_started` — this decision records that the two-model minimum's resource-channel *input* exists, not that M-F4-03 has run. The remaining ensemble slots (M-F4-02, OQ-009) still need to be chosen and acquired before J-1 can compute change factors for the full approved model set.
- **D-F4-008 — M-F1-05's reduction and reference period settled, no OQ opened (task F4-2, 2026-09-28).** Reduction: annual maximum of ERA5 `fg10` (10 m wind gust since previous post-processing), not `i10fg` and not a percentile — C2 (cut-out, tracker stow) concerns peak events, not a central tendency. Reference period: 1995-2014, coherent with S-05's reference climatology, since M-F1-05 declares the indicator scenario-invariant. Coverage check: ERA5 is production-quality from 1979, so 1995-2014 is fully covered at production quality; no shortening needed, nothing to stop for. Also settled: the daily-maximum reduction commutes with the annual-maximum reduction (`docs/phases/F1_data_acquisition.md` D-F1-016, verified by arithmetic on real probe data) — this justified requesting the CDS's own derived daily-statistics product at the time, though that product was later dropped for an unrelated operational reason (D-F1-017: the derived dataset itself proved unusable in real acquisition) in favor of computing the same commuted reduction locally over the raw hourly field. M-F1-05 no longer attributes to CRAEI (`docs/METHODOLOGY.md` v1.3.0) — CRAEI's own D12 decided against ERA5 gust, so there was nothing to adapt; the acquisition (task J-2 or a dedicated ERA5 task, TBD in staging) is built fresh.
- **D-F4-009 — M-F1-05's per-cell representation: annual maxima kept per year, the period-level scalar derived later (task F4-2, 2026-09-28).** The acquired/reduced product (`docs/phases/F1_data_acquisition.md` D-F1-017) is one annual maximum of `fg10` per cell per year, 1995-2014 (20 values per cell) — not collapsed to a single period-level scalar at acquisition time. The scenario-invariant indicator M-F1-05 describes (one context value per cell, attached to every member per M-F4-05) is the mean of those 20 annual maxima, a cheap pure-function aggregate over the small reduced product, computed whenever `hazard_context.parquet` is built (task J-4) rather than baked into the acquisition. Chosen over collapsing to a raw all-period maximum (a single extreme year would dominate, noisy) or re-downloading at a different aggregation later (the per-year granularity survives a change from mean to, say, a percentile, without another CDS acquisition). Per M-F4-05 (unchanged by this decision): the gust value enters F5/F6 quantitatively only if OQ-007 clears a Tier 1/2 loss function for C2; otherwise it is a context indicator reported in T-R10. This implementation does not assume OQ-007 resolves either way — nothing here computes a loss or feeds regret/satisficing.

- **D-F4-010 — OQ-036 resolved: hazard-channel ISIMIP3b data is copied into `GEOFREA_DATA_DIR`, route (b) (2026-10-05).** The 180-file projection channel (5 GCMs x 4 scenarios x 3 vars x 3 countries, 15.08 GB measured by direct disk inventory, matching the ~15 GB estimate in `docs/_audit/2026-09_craei_climate_reuse.md`) was copied once from CRAEI's raw root (`D:/Douglas/OUTROS/CRAEI_raw_data/raw/climate/isimip3b/`) into `GEOFREA_DATA_DIR/raw/isimip3b/<ISO3>/`, each file verified by sha256 against its CRAEI source during the copy (log: `GEOFREA_DATA_DIR/logs/_moves/oq036_isimip3b_copy_log.csv`, 180/180 `COPIED_VERIFIED`, zero mismatches). The 36-file W5E5 v2.0 reference channel (1.23 GB) was deliberately not copied: it is CRAEI's bias-adjustment target, not a projection product, and has no mapped consumer in any M-F4-0x item. Chosen over route (a) (read CRAEI's root in place) to keep A-08's "everything under `GEOFREA_DATA_DIR`" invariant intact and give GeoFREA a frozen, hashable copy independent of CRAEI's own archive still being actively filled; accepted cost is a manual re-copy if CRAEI later adds a combination GeoFREA needs. The copy is registered in `src/geofrea/data_acquisition/isimip3b_registry.py` / `GEOFREA_DATA_DIR/raw/isimip3b/isimip3b_registry.json` (180 entries, one per gcm/scenario/variable/country, sha256 reused from the copy log, not recomputed), built by the one-off `scripts/register_isimip3b_from_copy_log.py`. `paths.fetched_raw("isimip3b", iso3)` already resolved the correct directory with no code change needed. Open note for task J-1/`members.yaml` (D-F4-004): GFDL-ESM4 exists in both channels as two distinct source files (C1 = raw CMIP6 from F3-2; C2 = this ISIMIP3b copy) — `members.yaml` must declare this explicitly, not leave it to be inferred. Resolves OQ-036.
- **D-F4-011 — OQ-037 resolved: ERA5 gust's "day" stays the UTC calendar day; PRT scope is mainland only (2026-10-06, Douglas's verdicts).** UTC kept. Why it is safe: the annual maximum of the daily maximum equals the maximum over every hour of the year, so the day definition cannot change the value; it only decides which year the hours around 31 Dec/1 Jan belong to. Measured on IND, the worst case (UTC+5:30), 196 of 287,980 cell-years (0.068%) have their annual maximum inside the window that would move to a neighbouring local year, and even then the 20-year mean changes only if the neighbouring year's maximum differs. A local day would also need 31 Dec 1994 and 1 Jan 2015 downloaded and per-country timezone/DST handling, for no material effect. ERA5 `valid_time` is UTC by construction, so the product carries no timezone conversion. Resolves OQ-037. Scope decision, recorded here for the framework: Madeira and the Azores are not part of the analyses or the rest of the framework (PRT = mainland Portugal). Not yet applied anywhere — see OQ-039; the registered PRT ERA5 raster (39x89, 155 cells) still includes the island cells until that mechanism exists, after which regenerating it is a ~2 minute job from the retained year files.
