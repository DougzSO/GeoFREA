## 6. Área de pixel — geodésica vs. constante

**Cálculo geodésico real por latitude é usado**, centralizado em `src/geofrea/core/geodesy.py::wgs84_km_per_degree()` (`core/geodesy.py:27`). Consumido por:
- `data_quality_audit/raster_inspection.py::row_area_km2()` (`raster_inspection.py:114-133`) — calcula área por linha de pixel usando a latitude central de cada linha (não uma constante global), usado no cômputo de `area_km2`/`total_area_km2` de camadas raster (`raster_inspection.py:288-601`).
- `grid_alignment/vector_alignment.py:126-143` — distância geodésica linear a features (roads/grid/rivers), usando a latitude do centroide da grade (`lat_center`).
- `grid_alignment/alignment.py:292-301` — cálculo de área do país (`area_km2`) para a resolução "adaptive" (não usada em produção, ver `config/settings.yaml`), via `wgs84_km_per_degree(lat_mid)`.

**Constante não-geodésica usada deliberadamente em um único lugar**: `KM_PER_DEG_LAT = 111.32` (`core/constants.py:45`), usada **apenas** por `derive_slope_from_dem()` em `grid_alignment` para preservar paridade STRUCTURAL_PRESERVE com o cálculo de slope do legado (`core/constants.py:37-44`: "Deliberately NOT core.geodesy.wgs84_km_per_degree()... reproducing its numbers means using the same scale factor it used"). Este é o único ponto do código que assume um fator fixo em vez de geodésico — decisão documentada, não um descuido.

Nenhum outro módulo assume área de pixel constante sem justificativa registrada.

## 8. Orchestrator: `PhaseSpec`, formato do manifest, resumabilidade

Fonte: `src/geofrea/core/orchestrator.py` (323 linhas).

**Campos de `PhaseSpec`** (`orchestrator.py:152-168`, `@dataclass(frozen=True)`):
- `name: str` — deve casar com uma chave de `RunConfig.phases`.
- `output_model: type[BaseModel]` — o tipo Pydantic que `run` retorna; usado tanto para validar o resultado ao vivo quanto para reconstruir um `PhaseResult` tipado a partir do manifest ao retomar.
- `run: Callable[[PhaseContext], BaseModel]` — callable de um argumento (`PhaseContext`); inputs específicos da fase já devem estar vinculados (via closure ou `functools.partial`) por quem constrói o `PhaseSpec` — ver `main.py:252-260` para os closures reais (`grid_alignment_run`, `suitability_criteria_run`, `_audit_run`).

**Formato do manifest** (`orchestrator.py:96-121`): `outputs/<country_code>/manifest.json` (um manifest por país, não por invocação — `orchestrator.py:38-42`), schema `RunManifest` (`country_code: str`, `phases: dict[str, PhaseManifestEntry]`), onde `PhaseManifestEntry` tem `phase`, `status` (`"success"|"failed"`), `output: dict[str, Any] | None` (dict JSON solto, não tipado — `orchestrator.py:99-102`), `error: str | None`, `started_at`/`finished_at` (ISO-8601 UTC).

**Onde cada fase grava artefatos**: o manifest só registra o `output` serializado (`.model_dump(mode="json")`, `orchestrator.py:315`) — os artefatos de disco propriamente ditos (rasters `.tif`, PNGs, relatórios) são gravados pelas próprias funções de fase, fora do orchestrator:
- `suitability_criteria`: `outputs/<country>/suitability_criteria/{tif,figures}/` (`suitability_criteria/phase.py:181-185`).
- `data_quality_audit`/`grid_alignment`/`data_acquisition`: não lidos nesta auditoria linha-a-linha, mas seguem o mesmo padrão `outputs/<country_code>/<phase_name>/...` (confirmado pelo comentário do orchestrator em `orchestrator.py:38-42`, "mirrors legacy's own outputs/<code>/ layout").

**Uma fase consegue ler artefatos de uma execução anterior?** **Sim, via resumabilidade do manifest, não via leitura direta de artefatos de disco**: `Orchestrator.run()` (`orchestrator.py:224-323`) verifica, para cada `PhaseSpec` habilitado, se já existe uma entrada `"success"` no manifest carregado (`orchestrator.py:248-267`); se existir, reconstrói o `PhaseResult` tipado via `spec.output_model.model_validate(existing.output)` **sem re-executar** a fase, e o expõe em `results[spec.name]` — disponível para fases seguintes via `PhaseContext.prior_results` (`orchestrator.py:269-273`). Se não existir entrada `"success"`, a fase roda de fato (`orchestrator.py:277-278`) e o resultado é persistido no manifest (`orchestrator.py:290-320`) antes de seguir. Uma falha (`except Exception`) grava `status="failed"` no manifest e propaga `PhaseExecutionError`, **interrompendo todas as fases seguintes** — não há execução parcial após uma falha (`orchestrator.py:279-300`).
