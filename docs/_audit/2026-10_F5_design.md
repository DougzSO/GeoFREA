## 2. Proposed design

### 2.1 Principles

- **Pure functions in, tables out.** Each formula of M-F5-01 to M-F5-05 is a pure vectorized NumPy function that cites its item (A-13) and takes arrays and scalars. A thin pipeline reads parquet, validates the contract, calls the functions and writes parquet. No technology name appears (A-04): the technology picks a **CF model by the string** `cf_model` in the registry (`pvout_with_temperature`, `weibull_with_air_density`), through a dictionary `CF_MODELS` that maps the model name to its function.
- **Fail loud (A-09).** A missing parameter, an unknown `cf_model`, a hub height outside the data heights, a curve without a declared cut-out, a masked cell-member that is not declared, a CF outside [0, 1], or a NaN raises with the offending names. No clipping, no fallback.
- **Nominal parameters in F5; samples in F6.** F5 evaluates at the nominal `gamma` and `eta_loss`. F6 needs `CF(m, s)` for each sample `s`, which D8 solves without recomputing the integral.

### 2.3 The wind capacity factor, derived once so that the code is small

Weibull speeds form a scale family: `v ~ Weibull(A, k)` implies `c*v ~ Weibull(c*A, k)`. Therefore

- air-density correction: `integral P(c*v) f(v; A, k) dv = integral P(u) f(u; c*A, k) du` with `c = (rho/rho0)^(1/3)`. The density correction folds into the scale: `A_eq = A_H * (rho_H/rho0)^(1/3)`.
- climate change: `delta_wind` multiplies the speeds, so it multiplies the scale as well: `A_eq,m = delta_wind_m * A_eq`.

Hence `I(A_eq, k) = integral_0^inf (P_curve(u)/P_rated) f(u; A_eq, k) du` is a function of two numbers and a fixed curve; `CF0 = eta_loss * I(A_eq, k_H)`, `CF_m = eta_loss * I(delta_wind_m * A_eq, k_H)`, and the ratio form of M-F5-03 equals the direct form because `eta_loss` cancels. V-02 gets a test that the two forms agree to rounding. The density correction therefore needs no second integral and no per-cell curve shift.

### 2.4 Output format

Cell level, one file per technology and land scenario (D5):

`outputs/<ISO3>/technical_potential/artifacts/potential_<tech>__<scenario>.parquet`

| Column | Type | Meaning |
|---|---|---|
| `cell_id` | int64 | as in F3/F4 |
| `member` | category | `m0` or `m_<gcm>_<ssp>_<window>` |
| `P_MW` | float64 | M-F5-01; the same value in every member of a cell |
| `CF` | float64 | M-F5-02/03 (and M-F5-04 when a loss function exists), in [0, 1] |
| `E_MWh` | float64 | M-F5-05 |

Parquet schema metadata carries `geofrea_schema_version`, the scenario, the parameter values used (`LUF`, `PD`, `gamma` or `eta_loss`, `H`, power-curve id and hash, `rho0`, hours per year), the integration method (D1), `c2_applied: false`, and the counts of declared masked cell-members. Types: all float64, since V-03 requires country capacity to equal the sum of cell capacities and float32 sums would force a tolerance. Size for the largest case (BRA wind, 181,277 cells x 37 members = 6.7 M rows per scenario) is about 250 MB uncompressed, less with zstd.

Aggregates, one file per technology: `potential_aggregates_<tech>.parquet`, one row per (scenario, member):

`scenario, member, n_cells, n_cells_absent (masked), eligible_area_km2, P_GW, E_TWh, cf_energy_weighted (= E/(P*8760)), P_GW_like_for_like, E_TWh_like_for_like, delta_E_pct_vs_m0_like_for_like`.

The country is implicit (one manifest and output tree per country). The land range sits next to the climate effect by construction: the climate effect `member - m0` is computed inside each scenario, never across scenarios (U-08, D5).

Maps (T-R1, member-level maps exist for F4 and F5, A-08): not in M-F5-06; scope in D15.

### 2.5 Masked cells (M-F4-07)

1. Before any computation, `assert_forcing_usable(forcing, masked, candidate_cell_ids, members, wind_valid_range)` runs on each scenario's candidate set. It is the existing guard (D-F4-004) and raises if a candidate cell-member is neither a row of `forcing` nor listed in `forcing_masked`, or if a factor in the candidate cells is out of range.
2. A declared masked cell-member gets **no row** in `potential_<tech>__<scenario>.parquet`: the member is absent in that cell (M-F4-07), nothing is replaced. The count per member goes into the aggregates (`n_cells_absent`) and into the table metadata.
3. A member total over the cells that remain is not comparable with `m0`, because the cells dropped lower it for a data reason and not a climate reason. The aggregates therefore carry two series: the **all present cells** total, and the **like-for-like** total over the cells present in every member (D6). The climate effect of H5/T-R12 uses the like-for-like series.
4. F7 needs a rule for these cell-members too (V-03: "every cell of the F7 set is either ranked or in the climate-fragile class"). METHODOLOGY M-F7 does not mention masked cell-members today. F5 does not decide it; D6 lists it as an interface item that needs a METHODOLOGY line before F7.

### 2.6 Where the IEC power curve is stored

A table of 30 to 60 nodes per curve does not belong inline in `technologies.yaml`, but the registry is where A-04 and OQ-005 want the provenance. Proposal (D3, D4):

- `config/power_curves/<curve_id>.yaml`: one file per curve, validated by `PowerCurve` (id, IEC class, rated power, `nodes`, source, tier, `verified*` fields as in U-05, `synthetic`).
- `config/technologies.yaml` wind block: `power_curves: {<iec_class>: <curve_id>}` and `iec_class_rule`, both `null` until OQ-005 closes. The registry carries the provenance summary (curve id, source, tier); the file carries the table.
- The curve file's SHA-256 goes into the potential table metadata and the manifest entry (A-02), so a change of curve invalidates F5.
- Until OQ-005 closes there is **no curve for a real country**: wind F5 raises `MissingParameterError` for BRA, PRT and IND (fail loud). The only curve that exists is the synthetic one for ZZZ, stored under `tests/fixtures/` and not in `config/` (D3), flagged `synthetic: true`.

## 4. Decisions for the author's verdict

Numbered for reference ("D3: option b"). Each has options and a recommendation. D1, D2 (integration), D3 (synthetic curve) and D5 (scenarios) are the three the command asked for; the rest were found in the reading.

### D1. Integration of the Weibull against the power curve (method and step)

| Option | Description | For | Against |
|---|---|---|---|
| **a. Exact piecewise-linear (recommended)** | Treat the tabulated curve as piecewise linear. On each segment `P = m*u + c`, the integral is closed form: `m*A*Gamma(1+1/k)*[gammainc(1+1/k, t_b) - gammainc(1+1/k, t_a)] + c*[F(b) - F(a)]`, with `t = (u/A)^k` and `F` the Weibull CDF (`scipy.special.gammainc`). The tail beyond the cut-out is zero. | No step to choose; exact for the stored curve; cost is the number of nodes per cell-member; the V-02 comparison with `quad` then tests the formula, not a tolerance. | Needs care for very small `k`; the piecewise-linear reading of the curve is itself an assumption (it is the same one the other options make when they evaluate the curve between nodes). |
| b. Binned CDF | `CF = sum_j P(mid_j) * [F(u_{j+1}) - F(u_j)]` on a fixed speed grid up to the cut-out. | Simple; probabilities per bin are exact. | A step (for example 0.1 m/s) is a number the author must choose and defend; the cut-out discontinuity costs one bin of error. |
| c. Adaptive quadrature per cell | `scipy.integrate.quad` per cell-member. | Reference accuracy. | Too slow for 6.7 M cell-members (BRA wind); fine only as the test reference. |

Recommendation: **a**, with `quad` as the independent reference in V-02. If the author prefers b, the step and the tolerance are the verdict to give (suggest fixing the step by a halving test on the synthetic curve, with the tolerance written in the test). Either way the integral is evaluated once per `(A_eq, k)`; memory is one member at a time (D14).

### D4. Where curve provenance lives, and the IEC class rule

- Provenance: curve file carries the table and the U-05 provenance fields; `technologies.yaml` carries only the id, class and source summary (section 2.6). Recommended. The alternative (table inline in `technologies.yaml`) makes the registry unreadable.
- Class rule, three forms for OQ-005: (i) one class per country and technology; (ii) per cell, from the mean wind speed at hub height of the **reference climate**; (iii) per cell and per member (re-select under climate change). Recommendation: **(ii) with the class fixed across members**. A turbine is chosen for the site climate and not re-optimized for each future; re-selecting per member (iii) mixes a siting decision into the climate effect and makes `CF` discontinuous in the member. The class thresholds come from the IEC standard (Tier 1) and are the author's to supply and verify in OQ-005; I did not look them up.

### D5. P_MW: central scenario only or three land scenarios

Facts: `P_MW` depends on the scenario through `eligible_area_km2`, and `CF` too, because the resource attributes in the candidate tables are eligible-area-weighted means that change with the scenario. Only the central candidate set feeds F6 and F7 (V1, M-F3-04).

| Option | Description |
|---|---|
| a. Central only | One file per technology as M-F5-06 literally lists; the land range of the potential is computed from F3 areas without CF. Loses the land range of TWh. |
| **b. Cell-level for the three scenarios, one file each (recommended)** | `potential_<tech>__central.parquet`, `__restrictive`, `__permissive` (the F3 suffix convention). F6 and F7 read only `__central`. The aggregates table has the three scenarios, and the climate effect is computed inside each scenario. Meets U-08 (land range reported beside climate effects, not confounded) and the "three scenarios" wording of M-F5-06. Cost: three times the rows (about 20 M rows for BRA wind). |
| c. Central at cell level plus restrictive and permissive only as aggregates | Smallest output; the two other scenarios cannot be inspected per cell or mapped. |

Recommendation: **b**. This changes the output filename in M-F5-06, so it needs a METHODOLOGY changelog line under the change protocol; level (PATCH or MINOR) at the author's judgment (F3 made the same kind of change under 7.0.0).

### D6. Masked cell-members: what the aggregates report, and the F7 interface

- Aggregates carry both the all-present and the like-for-like series (section 2.5). Alternative: report only like-for-like. Recommendation: both, with the climate effect on like-for-like. The magnitude is known from D-F4-018: BRA masks 1.43% of cell-members at the range in force (0.5-1.5), PRT 0.0% and IND 0.0% (down to 0.6-1.4), so the choice matters for BRA only.
- F7 interface: M-F7 does not say what a masked cell-member is (not feasible? not defined? excluded from the member's regret?). F5 leaves it open and publishes the count. Recommendation: the author decides this before the F7 design; it needs a METHODOLOGY line (M-F7-01 or a new item).

### D7. Solar cell-members masked because of the wind factor

M-F4-07 masks the whole row when `delta_wind` is out of range, so a solar cell-member loses a valid `delta_rsds` and `dT` for a wind reason. `forcing_masked.parquet` holds only `delta_wind`, so F5 cannot recover the solar factors. Options: **(a, recommended) keep the literal rule**: the member is absent for both technologies in that cell, counted and reported per technology; **(b)** change F4 to mask per technology (two forcing files or a technology flag): a change to the F4 contract and METHODOLOGY (M-F4-06/07). Recommendation: a now; revisit only if the BRA count for solar is large enough to matter (F5 reports it).

### D8. Where `gamma` and `eta_loss` enter, given that F6 samples them

`gamma` and `eta_loss` are uncertain parameters sampled in F6 (U-03) and enter CF in F5. F5 stores the nominal-parameter CF (M-F5-06 columns). F6 can obtain `CF(m, s)` without re-integrating:

- wind: `CF(m, s) = CF(m, nominal) * eta_s / eta_nominal` (exact, because `eta_loss` is a scalar factor);
- solar: `CF(m, s) = CF(m, nominal) * (1 + gamma_s*dT) / (1 + gamma_nominal*dT)`, with `dT` read from `forcing.parquet`.

Options: **(a, recommended) F5 exports `rescale_cf_wind` and `rescale_cf_solar` (section 2.2) and F6 calls them**; the potential table keeps exactly the five columns of M-F5-06. (b) F5 writes extra columns (`cf_unscaled`, `dT`) so F6 reads one table; adds columns beyond M-F5-06 and duplicates the forcing. (c) F6 re-runs the full F5 CF models per sample: wasteful. Recommendation: **a**. The climate-fragile definition (M-F7-01) uses `CF(m, s0)` at the nominal parameters, which is exactly the F5 output.

### D9. Constants without a home: `rho0` and hours per year

M-F5-03 says "IEC 61400-12-1 convention" for `rho0` and M-F5-05 says 8760, neither with a stored value. Options: **(a, recommended) `core/constants.py`** with the standard cited in a comment, because both are physical or calendar constants and not scientific parameters with a range (U-05 has no use for a range here); **(b) `parameters.json`** with full provenance, as global entries. The author verifies the number either way (standing rule); this report does not enter it. Leap years are ignored by the definition `8760`; stated, not corrected.

### D10. The C2 hook (M-F5-04)

No loss function passed OQ-007, so no loss is applied. Recommendation: no code for `L_C2` now; the potential metadata states `c2_applied: false`. When OQ-007 passes, the registry gets a `c2_loss` entry per technology (a function id plus parameters with U-05 provenance), and the function multiplies `CF` after M-F5-02/03. An unused parameter path is not written ahead of its need.

### D11. How F5 declares the parameters it consumes

`LUF` and `PD` are not uncertain, so `--production` would not detect their absence. Options: **(a, recommended)** a `required_parameters` list per technology in `technologies.yaml` (`TechnologyConfig` has `extra="forbid"`, so the schema changes with it) and `core/production.py` checks it in a production run; keys `luf` and `power_density_mw_per_km2` in `parameters.json` (U-05 object, `range` allowed because OQ-004 wants variants). (b) F5 raises on its own when a key is absent, without registry support: works at run time but the production pre-check misses it. Recommendation: **a**, so a production run fails before any phase starts, as for the uncertain parameters.

### D12. Hub height: registry or parameters

`hub_heights` per country is in `technologies.yaml` (`null`). A hub height is a sourced scientific parameter (OQ-005) with a source and a verification, which `technologies.yaml` cannot hold in the U-05 form. Options: **(a, recommended) move it to `parameters.json`** as `hub_height_m` per country and wind (U-05 object), leaving the registry with the key name; (b) keep the registry as is. Recommendation: **a**; the domain rule is H in [100, 200] m (the data heights), anything else raises.

### D13. The fixture for F5 (A-06)

ZZZ has solar and wind layers but no CMIP6 inputs, so F4 cannot run on it. Options: **(a, recommended)** the F5 test builds a small `forcing.parquet` (and an empty `forcing_masked.parquet`, plus one declared masked cell-member) directly from the ZZZ candidate cells with round, known factors, so F5 is tested on the real F3 output of ZZZ; (b) extend `generate_zzz_fixture.py` with miniature CMIP6 NetCDFs so F4 also runs on ZZZ (closes the A-06 gap of F4 too; larger change). Recommendation: **a** for F5, and (b) as a separate item for F4 if the author wants it. The ZZZ test values (`LUF`, `PD`, `gamma`, `eta_loss`, hub height, the curve) follow the existing convention of round test values flagged as such in the ZZZ block of `parameters.json`; their numbers are chosen at implementation with the author.

### D14. Memory

The F5 working set is one member at a time: `(cells x curve nodes)` floats, about 90 MB for BRA wind with 60 nodes, and the rows of one member. No batching setting is needed, and A-10 names F6 and F7. Recommendation: per-member loop, no `memory` section in `settings.yaml` for F5; the section is created when F6 needs it (a value the author sets). If the author wants the bound declared now, the section needs a number.

### D15. Maps and rasters of F5

T-R1 (technical potential maps in MW/km2 of cell at the reference climate) and A-08 (member-level maps for F5) imply figures, and A-07 says rasters are COG, but M-F5-06 lists only tables. Options: **(a, recommended) tables only in the F5 implementation commit; a second commit adds the COG of `P_MW/cell_area` and `CF` at `m0` for the central scenario and the T-R1 figure**, under `settings.yaml` `figures`; (b) everything in one commit. Recommendation: **a**; separating the scientific table from the presentation keeps the diff reviewable.

### D16. The phase and the DAG

`PhaseSpec` for F5: requires `candidates_<tech>__<scenario>` tables (from F3), `forcing`, `forcing_masked`, `members` (from F4), the technology registry and parameters; produces `potential_<tech>__<scenario>` and `potential_aggregates_<tech>`. Because staleness follows content (A-02, 7.0.1), a rerun of F3 with unchanged candidate tables does not invalidate F5. The reference grid is not needed. Recommendation: as stated; no decision needed unless the author wants F5 to read the cell tables (`cells_<tech>__<scenario>`) instead of candidates (no reason found: candidates are the set F6/F7 use).
